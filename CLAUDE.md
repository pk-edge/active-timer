# TimeTracker (active-time)

Monorepo: desktop agent (Python/PySide6), FastAPI backend, Next.js dashboard.

## Codebase guide

`docs/CODEBASE_GUIDE.md` is this project's living codebase reference doc.

- **Read** the relevant section before making any non-trivial change.
- **Update** it in the same turn as any change that alters architecture,
  adds/removes a module, or changes a cross-cutting pattern (auth, data
  isolation, background jobs, caching, migrations).

## Permissions are part of every feature

No feature is complete until it is wired into RBAC, in the same change:

1. The `(module, action)` pair exists in `backend/app/core/permissions.py`
   (add the module or action there if none fits).
2. The endpoint is gated with `Depends(require("<module>", "<action>"))`.
3. The UI hides or disables the trigger behind `can("<module>", "<action>")`.

Backend-only gating is not enough — a visible button that 403s is a bug. When a
feature lives on one page but calls another module's API, gate it on the module
that owns the API (report buttons on the Devices page check `reports:view`).
See "RBAC" in `docs/CODEBASE_GUIDE.md` for the full rule.

## Git versioning — Conventional Commits + Semantic Versioning (REQUIRED)

Every commit in this repo MUST be a Conventional Commit, enforced by a `commit-msg` Husky hook
running commitlint. Version bumps and `CHANGELOG.md` are generated by semantic-release from those
commit messages — **never hand-edit the version field or `CHANGELOG.md`**.

**Tooling (root `package.json`, not `backend/`, `dashboard/`, or `agent/`):**
- `commitizen` + `cz-conventional-changelog` — interactive commit prompt: `npm run commit` (or global `git cz`)
- `@commitlint/cli` + `@commitlint/config-conventional` — enforces format via `.husky/commit-msg`, config in `commitlint.config.js`
- `husky` — wires the git hook (`git config core.hooksPath` → `.husky`)
- `semantic-release` + `@semantic-release/changelog` + `@semantic-release/git` — config in `release.config.js`, generates `CHANGELOG.md` and bumps `package.json` version on `master`. Configured for **local versioning + changelog only** — no npm publish, no CI wiring into `bitbucket-pipelines.yml` without the user's explicit sign-off.

**Commit message format:** `<type>(<scope>): <subject>`
- Types: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`
- Scope: module name — see the enum in `commitlint.config.js`. It mirrors `backend/app/core/permissions.py`'s module keys (`devices`, `reports`, `roles`, `users`, `groups`, `policy`, `audit`, `settings`, `files`, `tech`, `categories`, `activity`, `team`, `overview`, `home`, `logs`) plus stack-level scopes (`agent` for the desktop codebase, `backend`, `dashboard`, `installer` for both `installer/{macos,windows}` and the dashboard's Agents/installer-version page) and cross-cutting scopes (`auth`, `docs`, `ci`, `deps`, `release`)
- Breaking changes: `!` after type/scope (`feat(devices)!: ...`) or a `BREAKING CHANGE:` footer — triggers a major version bump
- `fix:` → patch bump, `feat:` → minor bump, `BREAKING CHANGE` → major bump — this is how semantic-release decides the next version, so the type must be accurate, not just descriptive

**Workflow:**
1. Stage changes as usual (`git add`).
2. Commit via `npm run commit` (launches the Commitizen wizard) — or write a Conventional Commit message by hand with `git commit -m "feat(devices): ..."`. The `commit-msg` hook rejects non-conforming messages before the commit is created.
3. To preview the next version/changelog without releasing: `npm run release:dry`.
4. Actual release (bump `package.json` version, write `CHANGELOG.md`, tag, commit) is run manually with `npm run release` until a CI pipeline is wired up.

This mirrors the global convention in `~/.claude/CLAUDE.md` (HRIS is the other reference
implementation); if the two ever conflict, this file wins for this repo. This machine also has a
**global git init template** (`~/.git-templates`, wired via `git config --global init.templateDir`)
that gives brand-new repos a baseline Conventional Commits check before Husky is even installed —
see the global CLAUDE.md's "Git versioning" section for how it defers to this repo's own `.husky`
hook once that's set up.

### Rule for any AI agent asked to commit in this repo

An agent cannot drive the interactive `git cz` wizard (it's a TTY prompt), so **write the Conventional
Commit message directly** in the `git commit -m "..."` call — do not fall back to a plain descriptive
message and do not use `--no-verify` to route around the `commit-msg` hook if it rejects the message;
fix the message instead.

- Format: `<type>(<scope>): <subject>` exactly as specified above, subject in imperative mood, no period, under ~72 chars on the summary line.
- Pick `scope` from the enum in `commitlint.config.js`; if none fit, omit the scope rather than inventing one outside the enum (commitlint will reject an out-of-enum scope).
- Pick `type` based on what actually changed, not how the task was described to the agent — `fix:` and `feat:` drive real version bumps, so misclassifying a fix as a `feat` (or vice versa) produces a wrong semver bump.
- A commit that includes a breaking change MUST carry `!` after the type/scope or a `BREAKING CHANGE:` footer — don't skip this even if the user didn't mention "breaking".
- Body/footer (e.g. `Co-Authored-By:`) still applies per the harness's own commit instructions — Conventional Commits only constrains the header line and optional footers, it doesn't replace the rest of the commit message conventions already in force.
- If the `commit-msg` hook rejects the message, treat that as a real validation failure to fix (reword and recommit), not an obstacle to bypass.
